# Project audit and development plan

Reviewed 10 September 2026 at commit f7fb5e6. Scope: Android build setup, protocol/models, USB/session lifecycle, configuration editing and writes, Compose screens, Room logging, exports, and existing tests. This document is the deliverable; application code has not been changed.

The project has useful separation between protocol, transport, persistence, and UI, and substantial protocol unit coverage. The next development cycle should focus on reliable connection ownership and trustworthy configuration writes. The current implementation does not support the README's claims of verified writes and complete recovery.

**Evidence and verification**

- The working tree was clean when the review began.
- There are 267 `@Test` annotations in nine protocol test files. No tests were found for transport/session behavior, configuration validation, viewmodels, persistence, exports, or Compose flows.
- Running `.\gradlew.bat test assembleDebug lintDebug assembleRelease --console=plain` in the checkout fails immediately: `Unable to access jarfile ... gradle-wrapper.jar`.

The Windows launcher then fails with `no main manifest attribute`, demonstrating that restoring only that version's JAR is insufficient; regenerate the wrapper bundle together.

Application sources and Gradle configuration were unchanged in that copy. The combined command finished in 15m 48s with exit code 1 because lint failed; individual results are below.
- JVM arithmetic reproduced the scaling truncation described in F04. The protocol write-tail discrepancy was checked against both archived language schemas.
- No Android UI, physical USB adapter, or BMS behavior was exercised. Code-path findings are distinguished below from device behavior that needs capture-based confirmation.

**Priority definitions**

P1 means a build blocker, incorrect configuration write, or broken core connection behavior to address before relying on the app. P2 means a functional or reliability defect to address before a broader release. Priority is an implementation recommendation, not a claim that physical damage has occurred.

**Findings**

**F01 · P1 · The build cannot be reproduced from a clean checkout.**

The missing/ignored wrapper JAR blocks every documented build/test command. Both launcher scripts use `-jar`; the verified 8.13 JAR requires the compatible wrapper launchers. The POSIX script also lacks its executable bit. Regenerate all wrapper files for the intended version, track the JAR through a narrow ignore exception, pin the distribution checksum, and verify fresh Windows/Linux checkouts. Evidence: [.gitignore](C:/Users/Horse/Documents/GitHub/jk-bms-usb/.gitignore:4), [Windows launcher](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/gradlew.bat:78), [wrapper properties](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/gradle/wrapper/gradle-wrapper.properties:3).

**F02 · P1 · Configuration downlink offsets disagree with the archived protocol schemas.**

The encoder writes read-side `enableFlags` at payload 281–289 and discharge under-temperature thresholds at 290–291. Both archived frame-04 definitions instead place those thresholds at 281–282, followed by ten reserved bytes. The prose reference's assertion that those fields match the read layout is inconsistent with those schemas. This discrepancy is confirmed; the actual device's accepted layout remains unverified. Separate read and write layouts, reconcile the reference with vendor captures, and add an independent literal golden frame. Evidence: [FrameEncoder](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/FrameEncoder.kt:72), [English schema](C:/Users/Horse/Documents/GitHub/jk-bms-usb/archive/en_US.json:1), [Chinese schema](C:/Users/Horse/Documents/GitHub/jk-bms-usb/archive/zh_CN.json:1), [conflicting reference](C:/Users/Horse/Documents/GitHub/jk-bms-usb/protocol-complete.md:436).

**F03 · P1 · Validation omits editable protection fields and is absent at the write boundary.**

`validateAll` checks only 19 values and omits recovery temperatures and protection delays exposed in Settings. An otherwise valid draft with charge overcurrent delay -1 can pass the UI gate and serialize as unsigned 0xFFFFFFFF. Several generic ranges also disagree with the reference. Build a shared typed schema covering every writable field, finite values, integer width, array sizes, and applicable threshold relationships; enforce it before any transport write. Validate model/firmware limits against evidence. Evidence: [validator](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/ConfigFieldValidator.kt:73), [UI validation gate](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/SettingsViewModel.kt:25), [write boundary](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:201), [unsigned encoder](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/FieldEncoder.kt:22).

**F04 · P2 · Saving one setting can shift untouched settings by a wire unit.**

Scaled floats are divided then truncated. JVM evaluation gives `3.3f / 0.001f -> 3299` after integer conversion; decoded raw 2000 can re-encode as 1999. Whole-frame writes therefore do not preserve untouched values exactly. Preserve raw integer values or use explicitly validated rounding. Tests must assert exact bytes across realistic voltage/current/capacity and negative-temperature values; existing one-unit tolerances can conceal this defect. Evidence: [scaled encoding](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/FrameEncoder.kt:26), [encoder test tolerance](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/test/java/com/horse/jk_bms/protocol/FrameEncoderTest.kt:84).

**F05 · P1 · Any valid frame can be accepted as a successful configuration write.**

The write path does not check the ACK frame code, parses its payload with the read parser, and returns success without issuing and comparing a configuration readback. A delayed runtime response can become a bogus config and a false success message. Define ACK handling from captures, reject unrelated responses, then verify actual applied values. Counter echo and ACK format are explicitly unresolved in the reference; do not hard-code assumed counter matching. Evidence: [ACK handling](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:219), [open protocol questions](C:/Users/Horse/Documents/GitHub/jk-bms-usb/protocol-complete.md:600).

**F06 · P1 · Polling and configuration writes can overlap on the serial port.**

`stopPolling` cancels without joining the active blocking USB read, and a write starts immediately. There is no transaction mutex or single queue. Responses can be consumed by the wrong reader. Caller cancellation can also bypass polling restart because cleanup is not in `finally`. Give one session component ownership of all exchanges, serialize reads/writes/refreshes, propagate cancellation, and restore only the intended polling state. Evidence: [poll cancellation](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:130), [write sequence](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:201), [blocking reads](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/usb/UsbSerialManager.kt:95).

**F07 · P1 · Manual connection has no USB permission flow.**

`openDevice` is called directly; there is no `hasPermission`/`requestPermission` path. Opening the app with an already attached adapter fails if permission was not previously granted through the USB attach intent. Add asynchronous grant/deny/detach handling before opening the port. Evidence: [connect](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/usb/UsbSerialManager.kt:50). Android documents this distinction in its [USB host guide](https://developer.android.com/develop/connectivity/usb/host).

**F08 · P1 · Disconnect and hotplug handling do not follow session lifetime.**

Disconnect only navigates; the repository shutdown function has no caller. The singleton may keep polling/logging with the port open. Successful navigation also removes the connection route, clearing the viewmodel that owns the only USB receiver. Detach handling, even when delivered, refreshes the picker without closing the active session. Move hardware-event ownership and selected-device identity to the session lifetime, explicitly shut down on Disconnect/detach, and suppress auto-reconnect after deliberate disconnect. Evidence: [navigation](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/ui/navigation/AppNavHost.kt:25), [Disconnect callback](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/ui/navigation/AppNavHost.kt:40), [receiver lifecycle](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/ConnectionViewModel.kt:106), [detach callback](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/ConnectionViewModel.kt:52).

**F09 · P2 · Reception cannot recover reliably from noise or a partial timeout.**

Transport returns fixed 300-byte blocks and discards partial reads. The decoder can only try offset zero in a 300-byte buffer. One prefix byte yields noise plus 299 frame bytes, leaving a trailing byte for the next transaction and potentially preserving misalignment indefinitely. Maintain a bounded receive buffer across reads, keep partial headers/frames, scan through corruption, and preserve subsequent frames. Evidence: [receive loop](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/usb/UsbSerialManager.kt:91), [frame search](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/FrameDecoder.kt:33).

**F10 · P1 · Settings can submit stale or invisible values.**

Invalid/empty text leaves the previous parsed draft intact, while the Write button validates that old draft. Separately, `BmsConfig.equals` uses identity, so identical polling snapshots become “unsaved changes”; the initial edit draft is retained until Reset or the settings viewmodel is recreated. This can overwrite externally changed settings. Store raw input, errors, baseline, and actual dirty fields explicitly; reconcile clean fields with fresh device data and display the exact submitted values. Handle decimal-comma locales consistently. Evidence: [input parsing](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/ui/screen/settings/SettingsScreen.kt:261), [dirty state and draft](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/SettingsViewModel.kt:22), [identity equality](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/model/BmsConfig.kt:50).

**F11 · P2 · The stale-data timer does not refresh the visible warning.**

`staleRefresh` is updated but never read in composition. Staleness and elapsed labels read the wall clock only when another observed state change triggers recomposition. When runtime updates stop, “Updated just now” can remain visible indefinitely. Derive age from observed ticking state and a monotonic clock, and expose stale/connected status consistently. Evidence: [dashboard clock](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/ui/screen/dashboard/DashboardScreen.kt:35).

**F12 · P2 · Logging creates duplicate fault history and unbounded snapshot tables.**

Every poll inserts config/device snapshots and every returned fault record with new IDs. Cleanup covers runtime/system logs only. Unchanged fault history becomes repeated events, and config/device/fault storage grows indefinitely. Deduplicate using validated device/event identity, record snapshots on change, and define retention for every table. Add session/device identity so data from multiple BMS units stays distinguishable. Evidence: [logging](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/repository/DataLogRepository.kt:36), [cleanup](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/repository/DataLogRepository.kt:91), [fault identity](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/local/entity/FaultRecordEntity.kt:9).

**F13 · P2 · Resource and persistence failures are not contained.**

Serial setup can acquire a connection/open port and then throw before assigning fields; the catch loses the locals without closing them. Logging and cleanup jobs also have no exception handling; a supervisor does not consume uncaught launch exceptions. Close partially acquired resources and turn storage failures into recoverable logging state. Evidence: [USB setup](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/usb/UsbSerialManager.kt:54), [background scope](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:69), [logging launch](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:164). See [Kotlin's coroutine exception rules](https://kotlinlang.org/docs/exception-handling.html).

**F14 · P2 · Export cannot be reopened after success/failure, and runtime CSV has a wrong column.**

The dashboard-scoped export viewmodel retains completion/error; the dialog immediately dismisses on that state each time it reopens. Errors are not displayed and `resetState` is unused. Independently, CSV labels a value `active_cells` but writes the highest-voltage cell index. Consume terminal events, support visible retry, and test the CSV schema against distinct sample values. Evidence: [dialog state](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/ui/screen/dashboard/ExportDialog.kt:26), [unused reset](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/ExportViewModel.kt:76), [CSV mapping](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/export/CsvFormatter.kt:14).

**F15 · P2 · System Logs never requests data; some runtime diagnostics are dropped.**

The Logs viewmodel only exposes state, the refresh method has no callers, and the poll sequence excludes system logs. Opening the screen therefore cannot populate it. Runtime parsing also reads then discards `cellWireResStat` and `enableFlags`, so those diagnostics never reach the model. Wire Logs entry/refresh into the serialized request queue and retain meaningful parsed diagnostics end to end. Evidence: [Logs viewmodel](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/viewmodel/OtherViewModels.kt:34), [refresh method](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/repository/BmsRepository.kt:48), [poll sequence](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/connection/BmsConnection.kt:99), [discarded wiring flags](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/RuntimeDataParser.kt:26), [discarded capability flags](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/protocol/RuntimeDataParser.kt:84).

**F16 · P1 · Database byte-array conversion uses APIs unavailable on supported Android versions.**

Room converters call `java.util.Base64` at lines 50 and 55, but the app declares minSdk 21 and does not configure core-library desugaring. Android lint reports four NewApi errors for these calls. On API 21–25, byte-array persistence reaches unavailable platform APIs, including normal config/device logging. Use a compatible codec while preserving the existing stored Base64 format, or explicitly configure and verify supported desugaring. Do not suppress the lint errors. Require codec round-trip and legacy-row tests on API 21/25 and a modern API, plus a passing lint run. Evidence: [converters](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/local/TypeConverters.kt:50), [minSdk and compile options](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/build.gradle.kts:15). Android documents [java.util.Base64 as API 26](https://developer.android.com/reference/java/util/Base64); [android.util.Base64](https://developer.android.com/reference/android/util/Base64) is available on the declared minimum SDK.

**Concrete work packages and acceptance tests**

1. **Build/CI package.** Regenerate all wrapper components for the selected Gradle version rather than following the stale 8.11.1 instruction in BUILD_STATUS. Fix the Base64 converter compatibility defect and test existing stored values on API 21/25 and a modern API. Check in the release ProGuard file already referenced by the build, deriving any keep rules from actual R8 output. Verify unit tests, Android lint, debug assembly and minified release assembly. Keep dependency upgrades in separately validated changes; no vulnerability conclusion was made from dependency age alone.
2. **Session/transport package.** Introduce an injectable transport interface and session state machine that distinguish disconnected, permission pending, connecting, live, stale, and recovery states. Use controllable dispatcher/clock/transport in tests. Cover grant/deny, unrelated detach, active detach, reconnect, navigation, double-connect, user disconnect, cancelled writes, and setup failures at each acquisition stage. Assert a maximum of one active exchange and no new transactions after shutdown.
3. **Framing package.** Replay fragmented headers, one-byte noise, partial read followed by timeout/late tail, corrupt frame followed by a good frame, back-to-back frames, and unrelated frame types. Require bounded memory, a deadline, and eventual recovery when valid data arrives. Verify counters only to the degree supported by device captures.
4. **Configuration package.** Use an independent golden downlink fixture with distinct values at payload 280–292. Assert exact preservation of unchanged shared field wire units; read and write payload tails have different layouts. Parameterize every writable field's limits, finite-number handling, integer representation, array sizes, and applicable protection/recovery relationships. Reject unrelated ACKs and readback mismatch. Test clearing text, malformed input, negative sign in progress, decimal-comma locale, equal polling snapshots, external changes, Reset, navigation cancellation, and repeated saves.
5. **Data package.** Replay the same 12-fault snapshot 100 times and verify event deduplication without conflating two devices. Preserve distinct events with identical measurements and test RTC reset/wrap/reconnect once device identity semantics are established. Test retention for all five tables, timestamp indexes, schema migrations, and failing DAO operations. Page queries and stream output to avoid retaining a whole history plus a second complete CSV/JSON representation in memory.
6. **UI/export package.** Advance time with no telemetry and require STALE to appear; verify disconnection clears prior-device data. Open Logs and observe one serialized request with loading/error/empty states. Complete two exports in one dashboard session; fail and retry another. Test a 16-cell dataset whose highest cell index is 3 and require active_cells = 16. Use UTC/millisecond timestamps, explicit units, device/session identity, specific MIME types, and distinct filenames.
7. **Hardware/release package.** Start with read-only captures on the actual JK-B2A20S20P and record firmware, adapter chipset and Android version. Resolve frame-length, write-tail, ACK, counter, timeout and error semantics against the vendor application. Validate a controlled configuration change plus readback and preservation of untouched fields. Exercise unplug/replug, background/foreground, permission loss, and an extended logging session. Expand the supported-adapter claim only with corresponding evidence.

**Additional recommendations and unresolved scope**

- Release readiness: [app build configuration](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/build.gradle.kts:21) references a missing `proguard-rules.pro`. No instrumented-test source, runner configuration, or CI workflow was found. These are setup gaps to resolve in phase 1; absence of custom keep rules alone does not establish a runtime R8 failure.
- Storage/privacy: [device entity](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/local/entity/DeviceInfoEntity.kt:22) persists setting credentials and the manifest enables backup without an explicit exclusion policy. Decide which credentials actually need persistence, mask revealable values by default, and define backup handling. No credential exposure was observed during this review.
- Database evolution: [database declaration](C:/Users/Horse/Documents/GitHub/jk-bms-usb/JkBmsApp/app/src/main/java/com/horse/jk_bms/data/local/JkBmsDatabase.kt:26) disables schema export. Enable schema tracking and migration tests before changing identity, indexes or retention schema.
- Malformed fault counts: parsing bounds records to 12 but can retain an advertised count above 12. Define reject/normalize semantics and test 0, 12, 13 and 255.
- Background monitoring: explicitly choose foreground-only monitoring or an Android-supported background session design. The present application-owned coroutine scope is not evidence that monitoring survives process/lifecycle changes.
- Documentation: remove “automatic read-back verification” and “all features implemented” claims until demonstrated. Reconcile README/CLAUDE/AGENTS/BUILD_STATUS around actual prerequisites, the 267 discovered tests, verified features, and remaining hardware assumptions. The committed daemon criteria request JetBrains JDK 21 despite README's generic “JDK 17+”; [Gradle documents daemon criteria precedence](https://docs.gradle.org/current/userguide/gradle_daemon.html).
- Product polish after correctness: review shared bottom navigation, accessibility labels, large fonts, rotation and small displays. These were not exercised and are verification tasks rather than confirmed layout defects.

**Release decision**

A monitoring preview should require phases 1–2, correct stale-state behavior, and successful read-only hardware validation. A release that permits configuration writes should additionally require phase 3's protocol, validation, transaction, and readback evidence. Broader release should require bounded logging, working export/Logs flows, and the minified release/device checks. Hardware uncertainty is a tracked dependency and must remain explicit in compatibility claims.
